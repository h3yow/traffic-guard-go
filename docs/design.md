# Traffic Guard：分层成本计费与运行期调整

本文档描述本版入口防护的额度口径（成本加权 + 三层叠加）、拒绝原因分层，
以及在不重启进程的前提下调整额度的兼容范围与验证方法。

## 1. 背景与要解决的问题

在“客户端突发/速率 + 全局在途 + 上游熔断”的基础上，本版解决三类线上问题：

1. 大客户重试占满全局名额，挤掉其他客户 → 引入**分组（租户）层**额度；
2. 不同接口处理成本不同，按“每次请求算 1 个”反映不出真实负载
   → 引入**按请求成本加权**核算；
3. 改额度要重启进程 → 支持**运行期热加载**，非法配置明确报错并沿用旧配置。

## 2. 按请求成本加权的计费口径

### 2.1 成本声明

- `endpoint_costs`：`入口名 -> 该入口一次受理消耗的额度（整数）`。
- **未声明或入口名为空一律按成本 1 计费**，旧配置不需要任何改动。
- 成本必须 `>= 1`；且不得大于任何一层（客户端/分组/全局）的最小上限，
  否则该入口在任何时刻都不可能被受理，`Validate` 直接判为非法配置。
- 入口名由接入方提供：HTTP 示例默认取 URL 路径，可用 `X-Endpoint` 头显式声明。

### 2.2 哪些额度按成本累计

速率窗、突发窗、在途量三类额度全部按**加权消耗**累计，而不是按请求个数：

- 突发窗：窗内所有已受理请求的成本之和 `<= burst`；
- 速率窗：滚动 1s 内所有已受理请求的成本之和 `<= rate_per_sec`；
- 在途量：当前已受理且未结束请求的成本之和
  `<= in_flight / global_in_flight`。

### 2.3 准入的原子性（all-or-nothing）

一次准入要同时检查所有“本次生效”的额度层（见第 3 节）。规则：

- 成本大于**任意一层剩余额度**时，请求被**整体拒绝**，绝不只占用一部分；
- 被拒请求**不扣任何额度**：窗口不追加、在途不增加；
- 只有六层全部通过时，才一次性记账（客户端与分组窗口各追加同一条目，
  客户端/分组/全局在途各加一次成本）。

### 2.4 归还：有且仅有一次

- 成功受理的请求在结束（含上游失败/超时/panic 收尾）时归还，
  且通过 `sync.Once` 保证**只归还一次**；
- 归还只减“在途量”，**不删除窗口条目**——窗口消耗是“准入即记账”，
  短请求完成不会把速率/突发额度重复吐出来；
- 因此不会出现“额度越用越多”（重复归还）或“漏还”（在途只增不减）。

### 2.5 高成本与普通请求混跑

判定顺序固定、单一临界资源，因此结论稳定可解释：
先判窗口（突发→速率）后判在途（分组→全局），同口径先客户端后分组；
没有分组归属的请求不经过分组层（见 3.1）。
例如全局剩余 4 时，一个成本 5 的请求被整体拒绝，全局仍为 4，
随后一个成本 1 的请求仍可正常进入。

## 3. 额度层次与拒绝原因分层

### 3.0 无分组归属时的默认口径（升级兼容）

**只有被 `groups` 显式配置的分组（含显式写出的缺省分组 `""`）才会对其成员
施加分组层的速率/突发/在途约束。** 客户端未出现在 `client_groups` 中、
或映射到不存在的分组时归入缺省分组 `""`；只要 `groups[""]` 没有被显式写出，
这些客户端就**不经过任何分组层**，完整保持升级前的口径：

- **客户端突发窗、速率窗各算各的**：一个客户端把自己的突发/速率用满，
  不会让其他客户端的正常请求被连带拒绝（不再被并成一份共享额度）；
- **唯一跨客户端的硬约束是全局在途总闸**：只有真把 `global_in_flight`
  占满时才影响所有人，结论固定为 `global_exceeded`，不会错报成分组层；
- 无分组归属时，`Snapshot.Explain()` 的分组段显示 `n/a`，
  且 `Snapshot.GroupEnforced == false`，运维可一眼确认本次判定不经过分组层。

### 3.1 归属到显式分组时：三层叠加

归属到某个显式配置分组的客户端，请求必须**三层都通过**才放行。
每层都有速率窗、突发窗、在途量三类额度，其中“客户端在途”用于观测/
防单客户堆积，硬上限的检查顺序为：

| 顺序 | 层 / 口径      | 拒绝原因常量                    | `X-Deny-Reason` 值          |
|----|--------------|-------------------------------|----------------------------|
| 1  | 客户端 突发窗   | `ReasonBurstExceeded`          | `burst_exceeded`           |
| 2  | 分组   突发窗   | `ReasonGroupBurstExceeded`     | `group_burst_exceeded`     |
| 3  | 客户端 速率窗   | `ReasonRateExceeded`           | `rate_exceeded`            |
| 4  | 分组   速率窗   | `ReasonGroupRateExceeded`      | `group_rate_exceeded`      |
| 5  | 分组   在途量   | `ReasonGroupInFlightExceed`    | `group_inflight_exceeded`  |
| 6  | 全局   在途量   | `ReasonGlobalExceeded`         | `global_exceeded`          |

其中第 2/4/5 项（分组层）只对归属到**显式分组**的客户端生效；
无分组归属的请求只经过第 1、3、6 项。因此：

- 无分组归属时，拒绝原因只会是 `burst_exceeded`、`rate_exceeded`
  （客户端自身窗口打满）或 `global_exceeded`（全局总闸打满），
  **绝不会出现 `group_*`**；
- 全局在途打满时，即使该客户端恰好在某个分组里，只要分组自身未满，
  结论也固定是第 6 项 `global_exceeded`（总闸兜底，责任不被错记到分组）。

此外保留既有的非额度结论：`circuit_open`（熔断打开）、`closing`（收尾中），
以及上游归一化类别 `success/timeout/conn_failure/business_err`。

### 3.2 分组（租户）配置

- `groups`：`分组名 -> {rate_per_sec, burst, in_flight, burst_window_ms?}`。
  该表中显式出现的分组才会施加分组层三层约束；
  **显式写出 `"groups": {"": {...}}` 即表示给缺省分组也开启共享额度**，
  此时未映射客户端确实共享该显式缺省分组的三层额度（管理员显式选择）。
- `client_groups`：`客户端标识 -> 分组名`。
- **未映射、或映射到不存在分组的客户端一律归入缺省分组 `""`，但只有
  `groups[""]` 被显式声明时它们才受分组层约束**；缺省分组未显式声明时
  （老配置、不写 `groups` 的情况），这些客户端只受自身窗口 + 全局在途约束，
  彼此互不挤占，即升级前的旧口径。
- `burst_window_ms` 取 0/缺省时继承顶层突发窗。

### 3.3 隔离性

- 每个显式分组独立维护窗口条目与在途计数器：**一个分组超额不影响其他分组**，
  也不会误伤没有分组归属的客户端；
- 没有分组归属的客户端之间同样隔离：窗口各自独立，
  唯一共享面是全局在途总闸；
- 全局层是所有请求共享的总闸：各客户端/各分组自己没超、但合计触顶时，
  结论是明确的 `global_exceeded`，而不是把责任错记到某个分组；
- 某层释放出的全局名额可被任意客户端/分组立即复用，
  不会出现一部分流量长期卡死另一部分。

### 3.4 可解释性

每次判定都会生成 `Snapshot.Explain()`，同时给出客户端层与分组层的
突发/速率窗加权已用量与上限、以及客户端/分组/全局三层在途加权量；
**没有分组归属时分组段显示 `n/a` 且 `Snapshot.GroupEnforced == false`**，
拒绝时还会附带“成本 N 将使已用量 X 超过上限 Y”的确定性说明。

## 4. 运行期调整（Reload）

### 4.1 使用方式

- 库：`guard.Reload(newConfig)`；限流器层面为 `limiter.Reload(newConfig)`。
- 进程：
  - 向进程发 `SIGHUP`，重新读取 `-config` 指定的文件；
  - 或 `POST /admin/reload`（便于脚本/探针验证），成功返回 200，
    失败返回 400 且**线上额度保持不变**。
- 未提供 `-config` 文件时热加载会明确报错（无可重读的来源）。

### 4.2 完整校验、失败回退

- 新配置先过 `Config.Validate()`（含未知字段拒绝、重复键拒绝、
  字段取值、成本可受理性、分组引用完整性等全部规则）；
- 任何非法项都返回错误，**继续沿用旧配置**，不会半生效；
- 校验在限流器内部也会再做一次，双重保证非法值进不了记账路径。

### 4.3 生效边界（确定且可复现）

- **不中断服务、不重启进程**：窗口历史与在途状态全部保留，只替换额度表；
- **已受理但未结束的请求按“受理时口径”收尾**：
  其成本与所属分组在受理成功时已固化进计费句柄（`Admission`），
  Reload 不改写、不重算。因此：
  - 改大/改小某入口成本，只影响 Reload 之后的新准入；
  - 调整客户端分组归属，旧请求仍归还到原分组、按原成本归还，
    不会重复计费，也不会静默丢弃；
- **缩容后的上限只约束 Reload 完成之后的准入判定**，
  不强行回收已占用名额：可能出现短暂“在途量高于新上限”，
  这些在途请求照常归还后，用量自然回落到新上限内，期间不允许新增超配请求；
- 窗口是“准入即记账”：Reload 前窗内的历史消耗仍计入新窗口判定，
  例如把 `rate_per_sec` 从 10 缩到 2，而当前 1s 窗内已消耗 5，
  则新请求立即被速率层拒绝，直到旧记录随时间滑出窗口；
- 熔断阈值/冷却随配置一并更新，但不清空当前熔断状态与连续失败计数。

### 4.4 兼容性

- 旧配置文件（无 `endpoint_costs/groups/client_groups`）行为与升级前完全一致：
  所有入口成本为 1，所有客户端**没有分组归属**，只受“自身突发/速率窗 +
  全局在途总闸”约束——客户端之间互不挤占，全局打满才报 `global_exceeded`；
  若要恢复“未映射客户端共享一份缺省分组额度”的行为，需在 `groups` 中
  显式声明缺省分组 `""`（这是明确的配置选择，而非隐式副作用）；
- `Guard.Serve` 增加了 `endpoint` 入参，
  `Snapshot` 由原 `ClientSnapshot` 以类型别名保留（`ClientSnapshot = Snapshot`），
  历史按字段名引用快照的代码仍可编译。

## 5. 配置校验规则汇总

- 顶层：`rate_per_sec>0`、`burst>0 且 <=rate_per_sec`、
  `0<burst_window_ms<=1000`、`global_in_flight>0`、
  `failure_threshold>0`、`open_cooldown_ms>0`、`upstream_timeout_ms>0`；
- 成本：成本 `>=1`，且不超过任何一层最小上限；入口名非空；
- 分组：速率/突发/在途均 `>0`，`burst<=rate`，
  `0<=burst_window_ms<=1000`（0=继承）；成本对每个分组都必须可受理；
- 归属：客户端标识非空；`client_groups` 的目标分组必须存在
  （缺省分组 `""` 永远可作为归属目标，但只有在 `groups` 中显式声明 `""`
  时才会对其成员施加分组层约束；不写 `groups` 即旧的“无分组”口径）；
- JSON：未知字段、重复键、尾随的第二个 JSON 值、类型不符一律拒绝。

示例见 [`config.example.json`](./config.example.json)。

## 6. 验证方法

### 6.1 自动化测试

- 成本加权：`go test ./... -run TestCost`
  - 未声明入口成本为 1；突发/速率窗按成本累计；
  - 成本超过剩余额度时整体拒绝且不扣任何额度；
  - 归还有且仅有一次；高成本/普通请求高并发下任意时刻在途不超额、最终归零。
- 分组分层：`go test ./... -run TestGroup`
  - 三层必须全过；六层拒绝原因两两可区分；
  - 分组互相独立、全局兜底边界确定；高并发下各分组/全局均不超额。
- 无分组默认口径：`go test ./... -run 'TestNoGroup|TestMixed|TestExplicitDefault|TestGuardNoGroup|TestGuardGroupedClients'`
  - 没有分组配置时，多个客户端的突发/速率窗各自独立、互不挤占；
  - 拒绝原因层次正确：自身窗口打满报 `burst/rate_exceeded`，
    全局在途打满报 `global_exceeded`（绝不报 `group_*`）；
    快照 `GroupEnforced=false`、`Explain()` 分组段为 `n/a`；
  - 显式声明缺省分组 `""` 时，未映射客户端确实共享该分组三层额度；
  - 有/无分组归属客户端高并发混跑：各分组、全局在途均不超额，最终精确归零；
    Guard 端到端（含熔断/收尾）口径与限流器一致。
- 运行期调整：`go test ./... -run TestReload`
  - 非法配置报错并沿用旧配置；缩容/扩容即时生效；
  - 窗口消耗跨 Reload 延续；在途请求按旧成本/旧分组收尾；
  - Reload 与大量并发受理/归还交错时在途非负、不越界、最终精确归零。
- 全量（含竞态）：`go test -race ./...`
- 既有用例（突发/速率恢复、全局上限、拒绝不计数、归还幂等、熔断/上游归类）
  保持通过，不回归。

### 6.2 手工冒烟（HTTP）

```sh
go build -o /tmp/traffic-guard ./cmd/traffic-guard
/tmp/traffic-guard -config docs/config.example.json -listen :8080 &

# 正常请求（入口默认取路径，成本命中 /v1/query=1）
curl -H 'X-Client-ID: acme' -i http://127.0.0.1:8080/v1/query

# 高成本入口
curl -H 'X-Client-ID: acme' -H 'X-Endpoint: /v1/bulk-export' -i http://127.0.0.1:8080/x

# 改配置文件后热加载
curl -X POST http://127.0.0.1:8080/admin/reload      # 或 kill -HUP <pid>
```

非法配置热加载时：接口返回 400，日志输出
`config reload rejected, keeping old config`，现有额度与在途请求不受影响。
