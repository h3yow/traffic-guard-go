# Traffic Guard：分层成本计费与运行期调整

本文档描述本版入口防护的额度口径（成本加权 + 三层叠加）、拒绝原因分层，
以及在不重启进程的前提下调整额度的兼容范围与验证方法。

## 1. 背景与要解决的问题

在“客户端突发/速率 + 全局在途 + 上游熔断”的基础上，本版解决三类线上问题：

1. 大客户重试占满全局名额，挤掉其他客户 → 引入**分组（租户）层**额度；
2. 不同接口处理成本不同，按“每次请求算 1 个”反映不出真实负载
   → 引入**按请求成本加权**核算；
3. 改额度要重启进程 → 支持**运行期热加载**，非法配置明确报错并沿用旧配置。

> 修订说明：分组功能上线初期把所有未配置分组的客户端隐式并入了一份
> 共享的“缺省分组”额度，导致老配置升级后客户端之间互相挤占、
> 且全局打满时拒绝原因误落在分组层。现改为：**只有在 `groups` 中显式
> 声明的分组才构成共享层**；未归属显式分组的客户端恢复“各自独立 +
> 全局在途总闸”的旧口径（见 3.0 节）。

## 2. 按请求成本加权的计费口径

### 2.1 成本声明

- `endpoint_costs`：`入口名 -> 该入口一次受理消耗的额度（整数）`。
- **未声明或入口名为空一律按成本 1 计费**，旧配置不需要任何改动。
- 成本必须 `>= 1`；且不得大于任何一层（客户端/分组/全局）的最小上限，
  否则该入口在任何时刻都不可能被受理，`Validate` 直接判为非法配置。
- 入口名由接入方提供：HTTP 示例默认取 URL 路径，可用 `X-Endpoint` 头显式声明。

### 2.2 哪些额度按成本累计

速率窗、突发窗、在途量三类额度全部按**加权消耗**累计，而不是按请求个数：

- 突发窗：窗内所有已受理请求的成本之和 `<= burst`；
- 速率窗：滚动 1s 内所有已受理请求的成本之和 `<= rate_per_sec`；
- 在途量：当前已受理且未结束请求的成本之和
  `<= in_flight / global_in_flight`。

### 2.3 准入的原子性（all-or-nothing）

归属显式分组的一次准入要同时检查六层（见第 3 节）；不归属显式分组的
请求只检查其中的客户端两层与全局一层（第 3.0 节）。规则一致：

- 成本大于**任一参与层剩余额度**时，请求被**整体拒绝**，绝不只占用一部分；
- 被拒请求**不扣任何额度**：窗口不追加、在途不增加；
- 只有全部参与层都通过时，才一次性记账（客户端窗口追加条目，
  客户端/全局在途各加一次成本；经过分组层时分组窗口与分组在途同样各记一次，
  不经过分组层则完全不触碰分组计数器）。

### 2.4 归还：有且仅有一次

- 成功受理的请求在结束（含上游失败/超时/panic 收尾）时归还，
  且通过 `sync.Once` 保证**只归还一次**；
- 归还只减“在途量”，**不删除窗口条目**——窗口消耗是“准入即记账”，
  短请求完成不会把速率/突发额度重复吐出来；
- 因此不会出现“额度越用越多”（重复归还）或“漏还”（在途只增不减）。

### 2.5 高成本与普通请求混跑

判定顺序固定、临界资源单一，因此结论稳定可解释：
先判窗口（突发→速率）后判在途（分组→全局），同口径先客户端后分组；
不经过分组层的请求则在窗口之后直接判全局在途。
例如全局剩余 4 时，一个成本 5 的请求被整体拒绝，全局仍为 4，
随后一个成本 1 的请求仍可正常进入。

## 3. 三层额度与拒绝原因分层

归属**显式分组**的客户端必须**三层都通过**才放行。每层都有速率窗、突发窗、
在途量三类额度，硬上限的六层检查顺序为：

| 顺序 | 层 / 口径      | 拒绝原因常量                    | `X-Deny-Reason` 值          | 适用客户端          |
|----|--------------|-------------------------------|----------------------------|--------------------|
| 1  | 客户端 突发窗   | `ReasonBurstExceeded`          | `burst_exceeded`           | 全部客户端           |
| 2  | 分组   突发窗   | `ReasonGroupBurstExceeded`     | `group_burst_exceeded`     | 仅显式分组成员       |
| 3  | 客户端 速率窗   | `ReasonRateExceeded`           | `rate_exceeded`            | 全部客户端           |
| 4  | 分组   速率窗   | `ReasonGroupRateExceeded`      | `group_rate_exceeded`      | 仅显式分组成员       |
| 5  | 分组   在途量   | `ReasonGroupInFlightExceed`    | `group_inflight_exceeded`  | 仅显式分组成员       |
| 6  | 全局   在途量   | `ReasonGlobalExceeded`         | `global_exceeded`          | 全部客户端           |

此外保留既有的非额度结论：`circuit_open`（熔断打开）、`closing`（收尾中），
以及上游归一化类别 `success/timeout/conn_failure/business_err`。

### 3.0 没有分组归属时的默认口径（老配置升级后的行为）

**没有任何分组配置的老配置（以及客户端未归属任何显式分组时），
客户端不经过第 2/4/5 项分组检查**，回到分组功能上线前的口径：

1. **每个客户端各算各的**：突发窗、速率窗按客户端独立记账，
   一个客户端把自己的突发/速率用满，只拒绝它自己，
   不会牵连其他本来没超量的客户端；
2. **全局在途是客户端之间唯一共享的总闸**：只有全部客户端合计把
   `global_in_flight` 占满时，才会影响所有人，且拒绝原因确定是
   `global_exceeded`，不会落到一个并不存在的“缺省分组”层；
3. 判定快照中 `Snapshot.GroupLayer == false`，`Snapshot.Explain()`
   输出 `group=<none>(group_layer=off)`，分组段字段全部为零，
   运维可直接据日志确认“该请求没有经过分组层”。

换句话说：**“缺省分组”不再隐式地把所有未映射客户端并成一份共享额度。**
只有在 `groups` 里显式声明了 `""` 分组时，未映射客户端才共享该组额度
（此时它就是一个与具名分组完全等价的真实分组）。

### 3.1 分组（租户）配置

- `groups`：`分组名 -> {rate_per_sec, burst, in_flight, burst_window_ms?}`。
  **只有在 `groups` 中显式声明的分组才作为共享租户层参与核算。**
- `client_groups`：`客户端标识 -> 分组名`。未出现在映射中的客户端
  不归属任何分组（走 3.0 的默认口径）。
- 缺省分组 `""`：
  - **未显式声明**（老配置即如此）：不构成共享层，未映射客户端
    各自独立、仅受全局在途总闸约束（见 3.0）；
  - **显式声明**：未映射、或在 `client_groups` 中显式映射到 `""`
    的客户端共享该组三层额度，行为与具名分组完全一致；
  - 显式声明时其额度不自动继承顶层，必须显式给出且通过校验。
- `burst_window_ms` 取 0/缺省时继承顶层突发窗。

### 3.2 隔离性

- 每个显式分组独立维护窗口条目与在途计数器：**一个分组超额不影响其他分组**，
  也不会误伤不归属任何分组、走默认口径的客户端；
- 不归属显式分组的客户端之间同样互不影响（各自独立窗口，没有共享在途层）；
- 全局层是所有请求共享的总闸：各客户端/分组各自没超、但合计触顶时，
  结论是明确的 `global_exceeded`，而不是把责任错记到某个分组；
  未分组客户端在该场景下也只会得到 `global_exceeded`；
- 某客户端/分组释放出的全局名额可被任意请求立即复用，
  不会出现一方长期卡死其他方。

### 3.3 可解释性

每次判定都会生成 `Snapshot.Explain()`，同时给出客户端层与分组层的
突发/速率窗加权已用量与上限、以及客户端/分组/全局三层在途加权量，
拒绝时还会附带“成本 N 将使已用量 X 超过上限 Y”的确定性说明。
未经过分组层的请求用 `GroupLayer=false` 与
`group=<none>(group_layer=off)` 明确标注，便于一眼区分
“分组层打满”与“未经过分组层、被全局总闸挡住”这两类结论。

## 4. 运行期调整（Reload）

### 4.1 使用方式

- 库：`guard.Reload(newConfig)`；限流器层面为 `limiter.Reload(newConfig)`。
- 进程：
  - 向进程发 `SIGHUP`，重新读取 `-config` 指定的文件；
  - 或 `POST /admin/reload`（便于脚本/探针验证），成功返回 200，
    失败返回 400 且**线上额度保持不变**。
- 未提供 `-config` 文件时热加载会明确报错（无可重读的来源）。

### 4.2 完整校验、失败回退

- 新配置先过 `Config.Validate()`（含未知字段拒绝、重复键拒绝、
  字段取值、成本可受理性、分组引用完整性等全部规则）；
- 任何非法项都返回错误，**继续沿用旧配置**，不会半生效；
- 校验在限流器内部也会再做一次，双重保证非法值进不了记账路径。

### 4.3 生效边界（确定且可复现）

- **不中断服务、不重启进程**：窗口历史与在途状态全部保留，只替换额度表；
- **已受理但未结束的请求按“受理时口径”收尾**：
  其成本、所属分组以及“是否经过分组层”（`Admission.groupLayer`）
  在受理成功时已固化进计费句柄，Reload 不改写、不重算。因此：
  - 改大/改小某入口成本，只影响 Reload 之后的新准入；
  - 调整客户端分组归属，旧请求仍归还到原分组、按原成本归还，
    不会重复计费，也不会静默丢弃；
  - Reload 新增/删除分组配置时，旧请求仍按受理时是否记账分组层
    决定是否归还分组计数器：未记账的不会多还，已记账的不会漏还；
- **缩容后的上限只约束 Reload 完成之后的准入判定**，
  不强行回收已占用名额：可能出现短暂“在途量高于新上限”，
  这些在途请求照常归还后，用量自然回落到新上限内，期间不允许新增超配请求；
- 窗口是“准入即记账”：Reload 前窗内的历史消耗仍计入新窗口判定，
  例如把 `rate_per_sec` 从 10 缩到 2，而当前 1s 窗内已消耗 5，
  则新请求立即被速率层拒绝，直到旧记录随时间滑出窗口；
- 熔断阈值/冷却随配置一并更新，但不清空当前熔断状态与连续失败计数。

### 4.4 兼容性

- 旧配置文件（无 `endpoint_costs/groups/client_groups`）行为与分组功能上线前
  完全一致：所有入口成本为 1，客户端突发/速率各自独立核算，
  唯一共享约束是全局在途总闸；**不会再被隐式并入一个共享的“缺省分组”**；
- 需要让未映射客户端共享额度时，在 `groups` 中显式声明 `""` 分组即可，
  属于显式 opt-in，不影响老配置的默认口径；
- `Guard.Serve` 增加了 `endpoint` 入参，
  `Snapshot` 由原 `ClientSnapshot` 以类型别名保留（`ClientSnapshot = Snapshot`），
  并新增只读语义的 `Snapshot.GroupLayer` 字段，
  历史按字段名引用快照的代码仍可编译。

## 5. 配置校验规则汇总

- 顶层：`rate_per_sec>0`、`burst>0 且 <=rate_per_sec`、
  `0<burst_window_ms<=1000`、`global_in_flight>0`、
  `failure_threshold>0`、`open_cooldown_ms>0`、`upstream_timeout_ms>0`；
- 成本：成本 `>=1`，且不超过任何一层最小上限；入口名非空；
- 分组：速率/突发/在途均 `>0`，`burst<=rate`，
  `0<=burst_window_ms<=1000`（0=继承）；成本对每个分组都必须可受理；
- 归属：客户端标识非空；`client_groups` 的目标分组必须存在
  （缺省分组 `""` 仅在显式声明于 `groups` 中时才是受约束的共享分组；
  未声明时未映射客户端不走分组层，不属于校验错误）；
- JSON：未知字段、重复键、尾随的第二个 JSON 值、类型不符一律拒绝。

示例见 [`config.example.json`](./config.example.json)。

## 6. 验证方法

### 6.1 自动化测试

- 默认口径（无分组归属）：`go test ./... -run 'TestUngrouped|TestExplicitDefault'`
  - 无分组配置时，客户端突发/速率窗互不共享，一方打满不影响他方；
  - 全局在途是唯一共享总闸，打满时未分组客户端的拒绝原因确定为
    `global_exceeded`（快照标注 `group_layer=off`），绝不误报成分组层；
  - 并发混跑下每个客户端稳定拿满自身突发额度，全局在途不超额、最终归零；
  - 显式声明的 `""` 缺省分组仍是真实共享分组（opt-in 口径）；
  - 热加载增删分组时，在途请求按受理时固化的“是否经过分组层”精确归还。
- 混跑隔离与全局兜底：`go test ./... -run TestMixed`
  - 显式分组成员仍受分组三层约束、组间互不影响；
  - 未分组客户端各算各的，两边互不误伤；全局打满时层次结论区分正确。
- 成本加权：`go test ./... -run TestCost`
  - 未声明入口成本为 1；突发/速率窗按成本累计；
  - 成本超过剩余额度时整体拒绝且不扣任何额度；
  - 归还有且仅有一次；高成本/普通请求高并发下任意时刻在途不超额、最终归零。
- 分组分层：`go test ./... -run TestGroup`
  - 三层必须全过；六层拒绝原因两两可区分；
  - 分组互相独立、全局兜底边界确定；高并发下各分组/全局均不超额。
- 运行期调整：`go test ./... -run TestReload`
  - 非法配置报错并沿用旧配置；缩容/扩容即时生效；
  - 窗口消耗跨 Reload 延续；在途请求按旧成本/旧分组收尾；
  - Reload 与大量并发受理/归还交错时在途非负、不越界、最终精确归零。
- 全量（含竞态，建议多跑几轮）：`go test -race -count=5 ./...`
- 既有用例（突发/速率恢复、全局上限、拒绝不计数、归还幂等、熔断/上游归类）
  保持通过，不回归。

### 6.2 手工冒烟（HTTP）

```sh
go build -o /tmp/traffic-guard ./cmd/traffic-guard
/tmp/traffic-guard -config docs/config.example.json -listen :8080 &

# 正常请求（入口默认取路径，成本命中 /v1/query=1）
curl -H 'X-Client-ID: acme' -i http://127.0.0.1:8080/v1/query

# 高成本入口
curl -H 'X-Client-ID: acme' -H 'X-Endpoint: /v1/bulk-export' -i http://127.0.0.1:8080/x

# 改配置文件后热加载
curl -X POST http://127.0.0.1:8080/admin/reload      # 或 kill -HUP <pid>
```

非法配置热加载时：接口返回 400，日志输出
`config reload rejected, keeping old config`，现有额度与在途请求不受影响。

### 6.3 本地手工验证“无分组默认口径”

用一份不含 `groups/client_groups` 的最小配置启动（例如临时把
`global_in_flight` 调小到 2 便于观察全局总闸）：

```sh
cat >/tmp/tg-legacy.json <<'JSON'
{"rate_per_sec":1000,"burst":1000,"global_in_flight":2}
JSON
go build -o /tmp/traffic-guard ./cmd/traffic-guard
/tmp/traffic-guard -config /tmp/tg-legacy.json -listen :18080
```

另开终端，用一个慢上游场景不易直接构造在途打满；可先验证“客户端互不挤占”——
即使把某客户端突发调低，不同 `X-Client-ID` 的结论彼此独立：

```sh
# 客户端各自独立：两个不同 client 并发请求不会互相挤占突发/速率
for i in 1 2 3; do
  curl -s -o /dev/null -w '%{http_code} %header{x-deny-reason}\n' \
    -H 'X-Client-ID: acme' http://127.0.0.1:18080/v1/query
done
for i in 1 2 3; do
  curl -s -o /dev/null -w '%{http_code} %header{x-deny-reason}\n' \
    -H 'X-Client-ID: globex' http://127.0.0.1:18080/v1/query
done
```

全局在途打满的确定性结论（`global_exceeded`、且日志里
`group=<none>(group_layer=off)`）建议直接看自动化用例
`TestGuardUngroupedGlobalDenyEndToEnd`，它用可控上游把两个请求卡在途，
第三个客户端必被全局层挡住且请求不到上游：

```sh
go test ./... -run TestGuardUngroupedGlobalDenyEndToEnd -v
```
